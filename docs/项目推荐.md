对，这个补充很关键。**按你现在的岗位定位，上一版 BudgetGraph-RL 确实做重了。**

你需要证明的不是：

> 我能够设计一种新的 RL 信用分配算法。

而是：

> 我能够设计一个真正可运行、可训练、可评测的 Agent 架构，并使用 GRPO 让 Agent 学会更合理地调用组件和管理状态。

因此，我会把最终推荐改成：

# 首选：ReMemR1-Lite

## 基于 GRPO 的主动记忆与上下文管理 Agent

更适合写成一个独立项目名：

> **MemAgent-RL：基于 GRPO 的主动记忆与上下文管理 Agent**

项目主体参考 **ReMemR1**，但不追求完整复现论文的大规模训练，也不再设计 GraphGPO、预算约束、图信用分配之类的新算法。

你的项目比例应该是：

* **70% Agent 架构与 Harness**
* **20% 训练、评测和实验工程**
* **10% GRPO 原理与配置**

# 为什么现在 ReMemR1 更适合你

ReMemR1 本身已经是一个完整的多轮 Agent，而不只是“对问答模型做 GRPO”。

它包含明确的 Agent 生命周期：

```text
start
  → 读取一段新上下文
  → Agent 决策
  → 执行 memory action
  → 更新环境状态与上下文
  → 继续下一轮
  → 输出最终答案
```

Agent 在每一轮可以产生：

* `<update>`：更新当前工作记忆；
* `<recall>`：从历史记忆中主动召回信息；
* `final answer`：结束任务并回答。

系统内部维护 current memory、history memory、recalled memory，并通过检索器执行 recall。训练时使用 GRPO，并组合最终回答正确性、动作格式和 memory update 的局部奖励。官方代码已经把 Agent 生命周期、异步 rollout、Retriever、Reward、Evaluation 等模块拆开了。([GitHub][1])

它还提供了完整代码、数据处理、3B/7B 训练脚本、评测脚本和 checkpoint，而不是只有论文；训练数据使用长上下文版本 HotpotQA，评测包含 HotpotQA 和 2WikiMultiHopQA。([GitHub][2])

这对你最大的价值是：**面试中大部分内容都可以围绕 Agent 讲，RL 只是用于学习 memory action policy。**

# 重新调整后的项目排名

下面是按你现在的目标重新评估后的工程判断：

| 项目                            | Agent 架构含量 | RL 难度 | 单卡缩小复现把握 | 最终建议             |
| ----------------------------- | ---------: | ----: | -------: | ---------------- |
| **ReMemR1-Lite**              |          高 |   低到中 |        高 | **首选**           |
| **AgeMem-Lite**               |         很高 |     中 |        中 | 第二选择，可借鉴其设计      |
| **AgentFlow-Lite**            |         很高 |     中 |       中低 | 架构最匹配，但风险更高      |
| **GraphGPO / BudgetGraph-RL** |          中 |     高 |        中 | 不再优先             |
| **Memory-R1**                 |         很高 |   低到中 |        低 | 官方代码仍未发布，不适合直接复现 |

AgeMem 的 Agent 架构比 ReMemR1 更丰富：它同时管理短期上下文和长期记忆，提供 Summary、Clear、Retrieve、Add、Update、Delete 六种工具，并设计了三阶段训练流程。但这也意味着更多工具、更多 reward 和更多训练阶段，单卡一个月内完整复现的风险更高。([GitHub][3])

AgentFlow 在岗位匹配度上可能最高，因为它由 Planner、Executor、Verifier、Generator 四个模块组成，只在线训练 Planner，并集成搜索、代码执行等多种工具。但它依赖更多模型角色、工具和外部服务，调试面明显大于记忆 Agent；官方仓库也需要配置搜索、Judge 和不同 LLM Engine。([GitHub][4])

Memory-R1 的两 Agent 架构也很漂亮：Memory Manager 学习 ADD、UPDATE、DELETE、NOOP，Answer Agent 负责记忆筛选与回答；但截至目前官方仓库仍标注“Code coming soon”，不能满足你直接复现、省时间的要求。([GitHub][5])

所以综合下来：

> **ReMemR1-Lite 不是 Agent 架构最复杂的，但它是 Agent 含量、代码完整度、硬件适配和成功概率之间最好的平衡。**

# 不建议纯复现，而是做一个“小而完整”的改造

原始 ReMemR1 主要有两类动作：

```text
update_memory
recall_memory
```

建议增加一个非常轻量、但很适合 Agent 架构面试的动作：

```text
compress_context
```

最终动作空间为：

```json
{"action": "update_memory", "content": "..."}
{"action": "recall_memory", "query": "..."}
{"action": "compress_context", "content": "..."}
{"action": "answer", "answer": "..."}
```

这不是 RL 算法创新，而是 **Agent 架构扩展**。

你的 Agent 架构可以设计为：

```text
长文档 / 多轮环境
        ↓
Context Chunker
        ↓
Context Builder
  ├─ 当前 observation
  ├─ Working Memory
  ├─ Recalled Memories
  └─ 剩余 Context Budget
        ↓
Qwen3.5-2B Policy Agent
        ↓
Action Parser / Dispatcher
  ├─ update_memory
  ├─ recall_memory
  ├─ compress_context
  └─ answer
        ↓
Memory Runtime
  ├─ Working Memory
  ├─ Historical Memory
  ├─ Retriever
  └─ Trajectory Logger
        ↓
下一轮状态
```

这样面试中就可以重点讲：

* Agent 状态如何维护；
* 工具调用协议如何设计；
* memory action 如何解析和执行；
* 工作记忆和历史记忆如何分层；
* Context Builder 如何避免上下文无限膨胀；
* Agent 如何避免重复 recall 和死循环；
* 如何记录完整 trajectory 并回放；
* 如何区分 Harness 问题、模型能力问题和训练问题；
* 如何评测 memory tool 是否真的产生收益。

这些明显比“我改了一个 advantage 公式”更符合你的岗位定位。

---

# GRPO 只需要做到这个程度

不需要改 GRPO，也不需要设计新的 advantage estimator。

对于同一道题，采样 4 条 Agent trajectory：

```text
Trajectory 1：update → update → answer
Trajectory 2：update → recall → answer
Trajectory 3：recall → recall → answer
Trajectory 4：update → compress → recall → answer
```

每条 trajectory 计算一个总 reward：

[
R =
R_{\text{answer}}
+\alpha R_{\text{format}}
+\beta R_{\text{memory}}
-\lambda R_{\text{cost}}
]

可以简单定义为：

* `answer reward`：最终答案 EM/F1；
* `format reward`：是否输出合法 action；
* `memory reward`：写入或召回的内容是否覆盖 supporting facts；
* `cost penalty`：无效调用、重复调用、上下文 token 数量。

然后使用标准 GRPO：

[
A_i =
\frac{R_i-\operatorname{mean}(R)}
{\operatorname{std}(R)+\epsilon}
]

这已经足够让你在面试中回答：

* 为什么选择 GRPO 而不是 PPO；
* GRPO 为什么不需要 Value Model；
* 同组采样是什么意思；
* 为什么一组 trajectory 全部 reward 相同时无法训练；
* KL penalty 有什么作用；
* reward shaping 为什么可能引发 reward hacking；
* 为什么需要 SFT cold start；
* rollout 数量和显存、方差之间有什么关系。

算法深度完全够用，同时不会挤占你做 Agent 系统的时间。

# 实验组应该围绕 Agent 架构设计

不再需要做 GraphGPO、GiGPO、加权最短路等大量算法组。

保留下面四到五组即可：

| 实验组                         | 作用                                  |
| --------------------------- | ----------------------------------- |
| **A：Base Model**            | 直接把全部可见上下文交给模型，不使用 memory agent     |
| **B：Fixed Memory**          | 固定滚动摘要，不允许模型自主决定 memory action      |
| **C：Prompted Memory Agent** | 有 update/recall/compress 架构，但不经过 RL |
| **D：GRPO Memory Agent**     | 相同架构，使用 GRPO 训练动作策略                 |
| **E：Ablation**              | 去掉 recall 或去掉 compress，验证组件作用       |

这个实验设计特别适合面试，因为可以把收益拆开：

[
\text{总收益}
==========

\text{Agent 架构收益}
+
\text{RL 策略优化收益}
]

例如：

* B 对比 A：固定记忆是否有效；
* C 对比 B：自主 memory action 是否有效；
* D 对比 C：GRPO 是否真的学到了更好的调用策略；
* E 对比 D：Recall、Compression 分别有什么贡献。

这比单纯比较 Base、GRPO、GraphGPO 更符合“Agent 架构岗”的思路。

# 评测指标也要以 Agent 为核心

## 最终任务效果

* EM；
* F1；
* 多跳问题成功率；
* 不同上下文长度下的准确率。

HotpotQA 本身具有多跳问题和 supporting facts 标注，适合自动计算回答效果，也适合检查 Agent 的 memory 是否覆盖关键证据。([HotpotQA][6])

## Agent 行为指标

* Recall 命中 supporting facts 的比例；
* 写入 memory 的信息精度；
* 无效 memory update 比例；
* 重复 recall 比例；
* 平均工具调用轮数；
* Agent 死循环率；
* Action 格式错误率；
* 平均上下文 token；
* 每个正确答案消耗的 token；
* 不同上下文预算下的准确率。

## 最有展示价值的案例

挑选一条需要跨多个 chunk 才能回答的问题，展示：

```text
第 1 轮：发现人物 A，写入 Working Memory
第 2 轮：发现事件 B，更新人物关系
第 3 轮：当前证据不足，Recall 第 1 轮记忆
第 4 轮：压缩无关上下文
第 5 轮：综合两段证据回答
```

然后对照未训练 Agent：

```text
不断覆盖旧记忆
→ 重复 recall
→ 最终遗忘早期证据
→ 回答错误
```

这种 trajectory 对 Agent 面试官非常直观。

# 5090 32GB 上的实施版本

## 模型选择

* **Qwen3.5-0.8B**：只用于验证 Agent 环境、动作解析、reward 和训练更新；
* **Qwen3.5-2B**：正式主模型；
* **Qwen3.5-4B**：主要实验完成后再考虑，不作为必须项。

## 建议初始配置

| 配置                     |                 建议值 |
| ---------------------- | ------------------: |
| 模型                     |          Qwen3.5-2B |
| 微调                     |           BF16 LoRA |
| LoRA rank              |              8 或 16 |
| 每题 rollout 数           |                   4 |
| 每次训练 prompt 数          |                 1～2 |
| 最大 Agent 决策轮数          |                 4～6 |
| 单轮生成长度                 |       96～160 tokens |
| Context 长度             |  先 8K，稳定后尝试 12K～16K |
| 文档 chunk               |        1K～2K tokens |
| 梯度累积                   |                8～16 |
| Gradient checkpointing |                  开启 |
| Reference model        | CPU offload 或限制显存占用 |

这一路线从模型规模上适合单张 5090，但 Agentic RL 的显存还取决于 rollout KV Cache、reference model、上下文长度和同时生成的轨迹数，因此应先用 0.8B 跑通，再切 2B，不能直接假定所有配置一次成功。

## 框架选择

原始 ReMemR1 仓库固定了较老的 vLLM 0.9 和 SGLang 0.4.6，因此直接把 Qwen2.5 替换成 Qwen3.5，可能碰到模型加载和 rollout 兼容问题。([GitHub][2])

更稳的路线是：

> **复用 ReMemR1 的 Agent Loop、Action Parser、Memory Runtime、Retriever、Reward 和数据，训练底座使用当前版 ROLL。**

ROLL 已在 **2026 年 6 月 3 日**加入 Qwen3.5 Dense/MoE 支持，同时面向多轮 Agentic Interaction，支持 vLLM/SGLang 和 LoRA。([GitHub][7])

并不是从零重写 ReMemR1。它最关键的实现集中在：

* MemoryAgent；
* TF-IDF Retriever；
* recurrent rollout；
* action/format reward；
* HotpotQA evaluation。

这些模块边界在官方仓库中已经比较清楚。([GitHub][1])

Qwen3.5 的迁移若持续卡在框架兼容性上，保底应立即换成 Qwen2.5-3B，而不是为了模型型号拖死整个项目。秋招项目最终看的是 Agent 架构、训练闭环和实验结果，不是底座名字是否最新。

# 最终决策

按照你“**Agent 架构为主、RL 经历为辅、单卡大概率跑通**”的真实诉求：

> **撤掉 BudgetGraph-RL，选择 ReMemR1-Lite，并增加一个轻量的 Context Compression/Context Budget Manager。**

最终项目的核心表述不是：

> 我改进了 GRPO。

而是：

> **我构建了一个可训练的长程 Agent 架构，并用 GRPO 让 Agent 学会何时写入、召回、压缩记忆以及何时结束任务。**

这比算法创新型项目更贴合你的现有实习、目标岗位和秋招面试叙事。
